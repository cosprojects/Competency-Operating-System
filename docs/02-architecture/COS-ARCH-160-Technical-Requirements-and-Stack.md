# COS-ARCH-160 — Technical Requirements and Technology Stack

## Назначение

Документ фиксирует технологические решения для первого публичного контура COS и правила их последующего развития. Он конкретизирует логические технологические домены из `COS-ARCH-150`, но не изменяет бизнес-границы, модель данных или ответственность прикладных сервисов.

Цель первого релиза — предоставить русскоязычный адаптивный веб-сервис, в котором человек анонимно проходит первичную диагностику, получает объяснимый профиль и рекомендации, а затем при желании сохраняет результат через вход по email magic link.

Документ не является планом разработки, каталогом библиотек или обязательством немедленно реализовать все перечисленные компоненты. Технология добавляется только тогда, когда её необходимость подтверждена предыдущим этапом продукта.

---

## 1. Архитектурные решения

### 1.1. Модульный монолит как стартовая форма

Первый продукт реализуется как модульный монолит в одном репозитории. Модули имеют явные границы и контракты, но развертываются как ограниченное число процессов. Это соответствует предметным границам COS и не создаёт операционную нагрузку микросервисной архитектуры до появления подтверждённой необходимости.

На MVP не используются:

- микросервисы и сервисная шина;
- Kubernetes;
- Kafka и другие выделенные event streaming-платформы;
- отдельная графовая БД;
- отдельное аналитическое хранилище;
- локальная LLM на основном production VPS;
- нативное Android-приложение.

Эти решения не исключены в будущем. Их внедрение требует измеримого ограничения текущей архитектуры, а не предположения о будущем масштабе.

### 1.2. Размещение и граница персональных данных

Персональные данные и результаты диагностики обрабатываются только в production-контуре на выбранном VPS:

```text
Пользователь
    ↓ HTTPS
Web application на VPS
    ↓ HTTPS / internal network
API и данные на VPS

Vercel
    └─ только статичный маркетинговый сайт без форм диагностики,
       сессий, токенов и доступа к пользовательской БД
```

Веб-клиент диагностики, API, авторизация, база данных и журналы аудита не размещаются на Vercel. Маркетинговый сайт не передаёт персональные ответы пользователя в аналитические или серверные функции Vercel.

### 1.3. Базовая инфраструктура

Минимальная конфигурация production VPS:

| Ресурс | Минимум для MVP | Назначение |
|---|---:|---|
| CPU | 4 vCPU | Web, API, PostgreSQL и фоновые задачи |
| RAM | 8 ГБ | Работа ОС, контейнеров, БД и Redis без AI-инференса |
| Диск | 100 ГБ NVMe | Данные, контейнеры, журналы и рабочий запас |
| Сеть | публичный HTTPS | Доступ к сервису; пропускная способность не является узким местом MVP |
| Backup | отдельное внешнее хранилище | Единственная допустимая копия данных не может находиться на VPS |

Эта конфигурация рассчитана на MVP без локального inference. При устойчивом дефиците памяти, места или времени ответа VPS масштабируется минимум до 16 ГБ RAM; AI при этом остаётся самостоятельным контуром.

## 2. Технологический стек MVP (Быстрый контур 2-недельного запуска и целевой контур)

Для запуска первой версии в течение **2 недель** силами малой команды с AI-агентами и Figma архитектура разделяется на **Fast-Track MVP (единый Next.js Fullstack-монолит)** и **Расширение Core-контура (выделенный NestJS/очереди при росте нагрузки)**. При этом доменные контракты (`Evidence → Competency State → Decision`) соблюдаются с первого дня.

| Область | Fast-Track MVP (2 недели) | Расширение (при росте нагрузки) | Роль и ограничение |
|---|---|---|---|
| Язык продукта | TypeScript | TypeScript | Единый основной язык web, API, контрактов и методического движка. |
| Прикладной контур (Web + API) | Next.js App Router (React + Server Actions / Route Handlers) + `shadcn/ui` | Next.js + выделенный NestJS API | На старте вся доменная логика изолирована в `src/modules/*` внутри единого приложения, что исключает двойной бойлерплейт. |
| Node.js runtime | Node.js 24 LTS | Node.js 24 LTS | Для production используются только LTS-релизы. |
| Бизнес-БД и Auth | PostgreSQL + Prisma (или Supabase Postgres + Magic Link Auth) | Выделенный PostgreSQL на VPS | Единственный источник истины для транзакционных бизнес-данных и версий решений. |
| Обработка артефактов (Evidence Ingestion) | Парсинг PDF/текста и ссылок на лету в нормализованный JSON (`Evidence`) + опциональный S3/Supabase Storage | Выделенный S3/MinIO object storage | Пользователь может приложить резюме/ссылку/описание проекта; если артефакта нет, сессия идёт по ветке `Self-Anchor + Work Sample`. |
| AI-экстрактор и проверка рубрик | **DeepSeek Flash V4 API** (`https://api.deepseek.com/v1`, OpenAI-compatible) + TypeScript AI SDK (`generateObject` + `zod`) + шлюз `ai-guardrails.ts` | Изолированный AI-adapter / локальный vLLM | LLM вызывается строго в 3 точках сессии (макс. 5 вызовов на сессию), возвращает только валидированный JSON по схеме. Итоговый `Level` и `Confidence` считает детерминированный TS-код. |
| Очередь задач | Синхронный / фоновый вызов без брокера | Redis + BullMQ | Redis и BullMQ подключаются только при появлении длительных фоновых пайплайнов. |
| Контейнеризация и прокси | Docker + Docker Compose + Caddy | Docker Compose + Caddy | Единый способ развёртывания с автоматическим TLS. |
| Резервные копии | Зашифрованные PostgreSQL dumps вне VPS | Зашифрованные PostgreSQL dumps вне VPS | Регулярное резервирование и проверка восстановления. |

### Осознанно отложенные компоненты

| Компонент | Когда появляется | Почему не нужен в 2-недельном MVP |
|---|---|---|
| Выделенный NestJS-сервис и Redis/BullMQ | После проверки первого сценария и роста фоновых задач | Внутри `Next.js` доменные модули (`evidence`, `profile`, `decision`) вызываются напрямую как типизированные сервисы без сетевых накладных расходов. |
| Полнотекстовый поиск | При росте каталога ресурсов и знаний | Каталог из 6 дизайн-треков Волны 1 и графа из 14 узлов хранится как версионированный JSON/TS-пакет `src/methodology/v1/`. |
| Аналитическое хранилище | При устойчивом объёме событий и корпоративной аналитике | Ранние продуктовые метрики (`Calibration Delta`, конверсия шагов, `Confidence`) собираются из операционной БД. |
| Графовая БД | Когда измерения покажут, что PostgreSQL не справляется с навигацией по графу | Связи «компетенция — микро-кейс — проверочный шаг» на MVP моделируются реляционно и в JSON-схемах методики. |
| Kubernetes и локальный GPU-кластер | При масштабировании и появлении высоких требований к пропускной способности | Docker Compose и вызовы через типизированный AI-контракт закрывают все задачи MVP. |

## 3. Структура репозитория и границы модулей

Для 2-недельного спринта допускается сборка в едином полнофункциональном приложении с чётким разделением доменных пакетов, которое при необходимости без переписывания бизнес-логики раскладывается на `apps/web` и `apps/api`:

```text
src/ (или apps/web + packages/*)
  app/                # 4 экрана MVP (Next.js App Router) и API Route Handlers
  modules/
    identity/         # анонимные сессии и сохранение профиля по email magic link
    consent/          # фиксация согласия на обработку данных и артефактов
    assessment/       # калибровка Self-Anchor (L0-L3), приём артефактов, выдача микро-кейса
    evidence/         # нормализация фактов из артефактов, STAR-ответов и рубрик микро-кейса
    profile/          # детерминированный расчёт Competency State (Level, Confidence, Calibration Delta, Target Gap)
    decision/         # подбор проверочного задания (Proof Task) для закрытия главного Gap
    audit/            # запись версий методики и оснований каждого решения
  methodology/
    v1/               # JSON-граф дизайн-треков Волны 1, якоря L0-L3, 12 микро-кейсов (ENTRY/PRACTICE)
```

### 3.1. Доменные модули

Каждый модуль владеет своей зоной ответственности и общается через строгие TypeScript-интерфейсы:

| Модуль | Владеет | Ответственность в Evidence-First MVP |
|---|---|---|
| `identity` | анонимные сессии, пользователи, magic links | Анонимный старт с первого экрана, привязка результата к email по желанию пользователя. |
| `consent` | согласия и версии документов | Ясное согласие на обработку ответов и загружаемых артефактов. |
| `assessment` | сессии оценки, `Self-Anchor`, выдача кейсов | Приём базовой самооценки (`L0–L3`), подбор адаптивного микро-кейса нужной сложности. |
| `methodology` | версии методики, граф нодов, 6 треков Волны 1, рубрики | Хранение дизайн-компетенций, поведенческих якорей и чек-листов двух полос кейсов. |
| `evidence` | происхождение и доверие к данным | Извлечение фактов из резюме/ссылок/описаний (с подтверждением пользователем) и проверка микро-кейса по рубрике. |
| `profile` | `Development Profile` и `Competency State` | Детерминированный расчёт `Current Level`, `Confidence`, `Calibration Delta` и `Target Gap` (включая сценарий без входных артефактов). |
| `decision` | `Adaptive Decision` и `Proof Task` | Выбор конкретного практического задания на 1–2 недели для создания недостающего артефакта. |
| `audit` | технически и методически значимые события | Сохранение `methodology_version`, `evidence_refs` и `rule_refs` для каждого расчёта. |

Generic-возможности — email, файлы, поиск, локализация, уведомления — не содержат уникальной бизнес-логики COS и используют зрелые инженерные решения по мере необходимости.

### 3.2. Локализация

MVP работает на одной локали — `ru`. Мультиязычность закладывается архитектурно, но английская версия в первый релиз не входит: домен и сайт компании двуязычные, а диагностика обкатывается на российских пользователях (`COS-BP-003`, раздел 8).

Правила, которые действуют с первого дня:

1. **Ни одной пользовательской строки в компонентах.** Все тексты интерфейса, письма, сообщения об ошибках и подсказки берутся из слоя локализации по ключу. Активная локаль одна, но ключи есть у всех строк.
2. **Локаль — параметр запроса, а не константа в коде.** Маршруты и письма строятся с учётом локали, чтобы добавление языка не меняло логику.
3. **Контент методики отделён от интерфейса.** Тексты кейсов, якорей и проверочных заданий живут в методическом пакете (`src/methodology/v1/`) вместе с графом, а не в слое интерфейса. Перевод методики — отдельная задача со своим версионированием.
4. **Определение страны по IP влияет только на маркетинговый сайт.** Диагностика локали не выбирает и данные за пределы РФ не отправляет.
5. **Дата, валюта, числа** форматируются по активной локали, а не строковой сборкой.

Добавление языка после первых инвестиций должно сводиться к добавлению каталога переводов и, отдельно, к переводу методического пакета — без правки доменных модулей.

## 4. Контракты и модель доверенного решения

### 4.1. Публичный контракт web → API

Веб-клиент взаимодействует с API только по HTTPS. Контракт версионируется в `packages/contracts`; API валидирует каждое входное сообщение.

MVP покрывает следующие операции:

1. создать анонимную сессию и получить согласие;
2. получить версию диагностического сценария;
3. сохранить ответ и завершить диагностику;
4. получить вычисленный профиль, объяснение и рекомендации;
5. по желанию создать аккаунт через email magic link и привязать результат;
6. получить, экспортировать или удалить сохранённые данные.

Токены, ответы и результаты не передаются через маркетинговый сайт, Vercel, URL-параметры или клиентские логи.

### 4.2. Контракт API → DeepSeek Flash V4 (Guarded AI Gateway, Экономия токенов и Защита от свободного чатинга)

В MVP используется ваш оплаченный ключ **DeepSeek Flash V4 API** через стандартный OpenAI-совместимый протокол (`@ai-sdk/openai` с `baseURL: "https://api.deepseek.com/v1"`). Чтобы исключить нецелевой расход баланса, обход правил оценки и превращение сервиса в бесплатный чат-бот, в коде (`src/methodology/v1/ai-guardrails.ts`) и БД (`AssessmentSession.aiTurnCount`, `totalTokensUsed`) действуют жёсткие технические ограничения.

#### 1. Бюджет токенов, ресурсы и фактическая стоимость 1 000 сессий

DeepSeek автоматически включает **Context Caching (Prefix Caching)** для одинаковых префиксов промпта длиной от 1024 токенов (скидка на кэшированный вход составляет ~80–90%). Поэтому функция `buildCacheOptimizedMessages()` всегда ставит статический блок инструкции и описания 14 узлов графа **первым сообщением `system`**, а меняющийся ответ пользователя передаёт во втором сообщении `user`:

| Шаг сессии (`AllowedAiStepType`) | Макс. вызовов на сессию | Вход (кэш + текст пользователя) | Выход (`max_tokens`) | Расход токенов на шаг |
|---|---:|---:|---:|---:|
| 1. `EXTRACT_PORTFOLIO_FACTS` (только если загружено портфолио/CV) | `0` или `1` | ~1 200 (кэш) + до 900 (`<= 3500 симв.`) | до `400` | ~1 500 – 2 500 |
| 2. `EVALUATE_MICRO_CASE` (проверка ответа по 4 пунктам рубрики) | строго `1` | ~1 200 (кэш) + до 550 (`<= 2200 симв.`) | до `500` | ~1 600 – 2 250 |
| 3. `SCOPED_NODE_QA` (уточняющий вопрос по конкретному ноду на Экране 3) | от `0` до `3` | ~1 200 (кэш) + до 130 (`<= 500 симв.`) | до `350` | ~1 500 за вопрос |
| **ИТОГО на 1 полную сессию пользователя** | **Максимум 5 вызовов** | — | — | **~3 500 – 10 510 токенов (потолок в БД: `12 000`)** |

- **Экономия без портфолио:** если пользователь на Экране 1 не загрузил резюме/ссылку, шаг `EXTRACT_PORTFOLIO_FACTS` **не вызывается вообще** (0 токенов).
- **Экономия на парсинге файлов и ссылок:** PDF-резюме разбирается локально на сервере (извлечение чистого текста без картинок и верстки, обрезка до 3 500 символов), прежде чем попасть в DeepSeek.
- **Фоновый мониторинг сферы (`Market Pulse Worker`):** запускается **не на каждого пользователя**, а по расписанию (1 раз в неделю, 14 нодов × 1 запрос = ~25 000 токенов в неделю), обновляя веса в БД для всех пользователей сразу.

**Фактическая стоимость.** Тариф вынесен в единственную константу `DEEPSEEK_PRICING_USD_PER_MTOKENS` (`src/methodology/v1/ai-guardrails.ts`), стоимость считается функцией `estimateTokensCostUsd()`. Источник — https://api-docs.deepseek.com/quick_start/pricing: при подтверждении тарифа модели V4 Flash достаточно заменить значения в одном месте.

| Сценарий на одну сессию | Токенов | $ на 1 000 сессий |
|---|---:|---:|
| без портфолио, только разбор кейса | 2 250 | 0.78 |
| типичная (портфолио + кейс + 1 вопрос) | 6 430 | 2.05 |
| максимум (портфолио + кейс + 3 вопроса) | 10 510 | 3.55 |

Расчёт по опубликованному тарифу `deepseek-chat` (кэш-хит $0.07, промах $0.27, выход $1.10 за 1M токенов). Скидка на кэшированный вход — **≈74%**, а не 80–90%: префиксное кэширование не распространяется на выходные токены, а они дают основную часть счёта. Корректный порядок — **единицы долларов на 1 000 сессий**, то есть ≈$0.002 за сессию. Прежняя оценка «менее $0.50» была занижена.

#### 2. Защита от свободного чатинга и обхода правил (Anti-Abuse & Anti-Jailbreak)

**Статус.** Уровни 3, 4 и 6 реализованы и покрыты тестами. Уровни 1, 2 и 7 описаны как целевая архитектура: HTTP-слой (`app/`, route handlers) ещё не создан, поэтому атомарный инкремент счётчиков и rate limit по IP делаются вместе с ним. Уровень 5 ждёт реализации вызова модели — сейчас в `src/` нет ни вызова LLM, ни использования `zod`.

1. **Отсутствие «свободного чата» в архитектуре API:**
   Сервер принимает только типизированный вызов с обязательным `stepType` (`EXTRACT_PORTFOLIO_FACTS` | `EVALUATE_MICRO_CASE` | `SCOPED_NODE_QA`); эндпоинта `/api/chat` с произвольной историей переписки не предусмотрено. Для `SCOPED_NODE_QA` обязателен валидный `targetNodeIdForQa` из графа — без привязки к узлу запрос отклоняется до вызова LLM (реализовано в шлюзе; HTTP-слой — в разработке).
2. **Счётчики и квоты (`AssessmentSession.aiTurnCount`, `totalTokensUsed`):**
   Шлюз `validateGuardedAiRequest()` отказывает без обращения к DeepSeek API при исчерпании общего лимита (5 ходов), бюджета токенов (`12 000`) **и квоты конкретного шага** (`EXTRACT` — 1, `EVALUATE` — 1, `SCOPED_NODE_QA` — 3). Атомарный инкремент счётчиков в строке сессии делает вызывающий код — он появится вместе с HTTP-слоем.
3. **Серверный фильтр инъекций и оффтопа до вызова модели (`0 потраченных токенов`):**
   Регулярные правила в `ai-guardrails.ts` отсекают смену роли и снятие инструкций, выпрашивание оценки и явный оффтоп — на русском **и** на английском (*«ignore the rules above», «выстави мне L3», «write me a Python script»*), а также слишком длинные простыни текста. Это денилист: он не заменяет системный промпт и не является тематическим классификатором.
4. **Обезвреживание служебных тегов (`<user_untrusted_data>`):**
   Функция `escapeIsolationTags()` сначала заменяет корректную форму тега, затем — само имя тега, поэтому варианты с пробелом перед `>`, с переводом строки, в другом регистре и вложенные конструкции не проходят. Оставшийся текст оборачивается в контейнер `<user_untrusted_data>`, и системный промпт фиксирует: всё внутри — проверяемые данные, а не инструкция.
5. **Принудительный JSON-выход (`response_format: { type: "json_object" }` + `Zod`) — не реализовано.**
   Целевое состояние: ответ обязан пройти валидацию схемы `DualLoopChatResponseContract`, и модель физически не может «поболтать» свободным текстом. Сейчас в `src/` нет вызова модели и нет использования `zod`; это первый пункт к реализации при подключении API.
6. **Полное отделение LLM от выставления оценки:**
   Даже если пользователь попытается убедить модель в тексте ответа, LLM возвращает только совпадения с 4 наблюдаемыми критериями рубрики (`matchedRubricItems: number[]`), а итоговый `verifiedLevel`, `Confidence` и `Calibration Delta` вычисляет детерминированная TypeScript-функция `evaluateCompetencyNodeState()`. В контракте ответа нет полей уровня и уверенности.
7. **Rate Limit по IP и `anonymousToken` — не реализовано.**
   Целевое состояние: через Caddy / Middleware ограничивается создание новых анонимных сессий (не более 3 сессий с одного IP в час), чтобы исключить скликивание баланса ботами. В репозитории нет ни middleware, ни конфига прокси.
8. **Видимый ответ чата не раскрывает оценку кейса.**
   Пока ответ на микро-кейс не оценён по рубрике, `replyToUser` не подтверждает и не опровергает ни один пункт `rubricChecklist`: ни прямо («верно», «ты упустил третий пункт»), ни по смыслу (перечисление правильного решения). Модель говорит только о том, что принято к разбору, и о следующем шаге. Разбор по пунктам показывается после оценки и только в паспорте (`COS-RES-008`, раздел 7.4). Ответ на кейс — единственный объективный сигнал в сценарии, и подсказка его обесценивает.

### 4.3. Версионированная запись решения

Каждое опубликованное решение хранит минимум:

| Поле | Назначение |
|---|---|
| `methodology_version` | Воспроизводимость правила и интерпретации. |
| `evidence_refs` | Какие доверенные сведения участвовали в расчёте. |
| `state_snapshot` | Текущее оценённое состояние компетенций и confidence. |
| `rule_refs` | Правила и политики, применённые при выборе действия. |
| `selected_action` | Выбранный следующий шаг развития. |
| `explanation` | Человеко-читаемое обоснование решения. |
| `calculated_at` | Время и контекст вычисления. |

Это реализует принцип ADE: решение проходит trusted information, анализ состояния и gap, проверку правил, выбор, валидацию, объяснение и публикацию. Состояние компетенции вычисляется на основе evidence и методики, а не произвольно перезаписывается.

## 5. Патентный контур и адаптивный маршрут

Патент РФ `RU2863772C1` описывает формирование персонализированной образовательной среды из существующих ресурсов и адаптивное изменение последовательности изучения по мере получения результатов. В COS этот принцип реализуется как часть Development Engine, но не ограничивает продукт образовательными курсами.

Для реализации патентной логики система должна поддерживать версии следующих объектов:

```text
Ресурс / действие развития
        ↓ связан с
Темой и компетенцией
        ↓ входит в
Шаг маршрута
        ↓ порождает
Результат и evidence
        ↓ влияет на
Состояние компетенции
        ↓ пересчитывает
Следующее adaptive decision
```

Требования MVP:

- методика и её связи не меняются «задним числом»: новое изменение создаёт новую версию;
- результат диагностики сохраняет ссылку на использованную версию методики;
- пересчёт маршрута создаёт новое решение и не стирает предыдущее;
- пользователь видит основание рекомендации и может дать обратную связь;
- PostgreSQL хранит рёбра этой модели в реляционных таблицах и обеспечивает целостность ссылок.

Графовая БД не нужна, пока нет измеримого ограничения на сложность маршрутов, глубину обхода или время запросов. Решение о её добавлении принимается только по фактическим метрикам.

## 6. AI-стратегия

### 6.1. Порядок внедрения

1. **Rule-based MVP.** Decision Engine на TypeScript применяет утверждённую версию методики и формирует структурированный, объяснимый отчёт без LLM.
2. **AI как слой изложения.** После валидации полезности результата добавляется локальный adapter для более естественного объяснения уже принятого решения.
3. **Инференс на отдельном узле.** CPU-режим использует `llama.cpp` и квантованную модель; при наличии подходящей NVIDIA GPU используется отдельный runtime `vLLM`. У узла собственные лимиты, журналы и политика обновления моделей.
4. **Обучение только после оценки.** Fine-tuning возможен при наличии легально полученного и размеченного набора данных, baseline, safety/evaluation-набора, воспроизводимого запуска и измеримого улучшения над базовой моделью.

### 6.2. Запреты и проверки AI

- Нельзя обучать модель на защищённых вопросах, ключах или нормативах тестов без разрешения правообладателя.
- Научные публикации и открытые материалы используются только при понятном правовом основании; сохраняются источник и версия.
- Модель не ставит медицинских, психотерапевтических или кадровых диагнозов и не принимает решения о найме.
- До публикации пользовательского текста проверяются структура, запрещённые утверждения, ссылки на методику и отсутствие неоснованных обещаний.
- Модель и prompt имеют версии; каждый эксперимент можно сопоставить с baseline и откатить.

### 6.3. Критерий подключения AI в продукт

AI выводится пользователю только если он показывает измеримое преимущество над rule-based формулировками на заранее утверждённом наборе кейсов, не изменяет решение движка и проходит проверки безопасности, ясности и научной корректности. Недоступность AI не должна блокировать завершение диагностики или получение результата.

## 7. Эксплуатационные и безопасностные требования

### 7.1. Production minimum

- Все production-компоненты запускаются из закреплённых Docker-образов через Docker Compose.
- Caddy выдаёт и обновляет TLS-сертификаты; наружу открыты только необходимые HTTP(S)-порты.
- PostgreSQL, Redis и внутренние служебные порты не доступны из интернета.
- Секреты не коммитятся в Git, не входят в образы и передаются через защищённые production-переменные или secret store.
- API применяет rate limit, валидацию входных данных, защиту сессий и разрешения на уровне пользователя.
- Health checks проверяют web, API, БД и Redis; отказ одной фоновой задачи не делает API недоступным.
- Логи содержат технические идентификаторы и ошибки, но не тексты ответов, email, magic links или полные результаты диагностики.

### 7.2. Резервные копии и восстановление

- Выполняются регулярные зашифрованные дампы PostgreSQL во внешнее хранилище.
- Backup-ключи, доступ к VPS и ключи приложения разделены.
- Документируется runbook восстановления: новая чистая среда, восстановление базы, проверка целостности, ротация скомпрометированных секретов и проверка доступности сервиса.
- Восстановление проверяется периодически в тестовой среде; успешный backup без проверки восстановления не считается достаточным.

### 7.3. CI/CD

GitHub Actions выполняет проверки TypeScript, тесты и сборку контейнеров. Развёртывание в production допускается только после успешной сборки и с возможностью вернуть предыдущий образ. Изменения схемы БД применяются миграциями Prisma и имеют проверенный сценарий rollback или forward-fix.

## 9. Критерии готовности к первому публичному запуску

### Продукт и данные

- Диагностика выполняется анонимно, а сохранение результата требует явного согласия и входа.
- Пользователь может экспортировать и удалить сохранённый профиль.
- Каждый результат связан с версией методики, evidence и объяснением.
- Основной отчёт доступен без AI-adapter.

### Инфраструктура

- Production VPS соответствует минимуму 4 vCPU / 8 ГБ RAM / 100 ГБ NVMe и не запускает локальную LLM.
- TLS включён; БД, Redis и служебные порты закрыты от публичной сети.
- Есть успешный тест восстановления backup на отдельной среде.
- Health checks, rate limiting и структурированное журналирование включены.
- Статичный сайт на Vercel не имеет доступа к пользовательской БД, токенам, ответам или результатам.

### Методика и AI

- Методика, источники и правила версионированы и проверены до публикации.
- Использование каждого теста и источника имеет понятное правовое основание.
- В отчёте явно отделены данные пользователя, оценка, степень уверенности и рекомендация.
- Подключение AI возможно только после прохождения критериев из раздела 6.3.
