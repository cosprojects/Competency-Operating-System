# COS-ARCH-171 — приёмка материалов при масштабе

## 0. Проблема

При 100 профессиях и ежедневных обновлениях человек как **гейт** приёмки
не масштабируется: очередь либо тормозит публикацию, либо подтверждается не глядя —
и создаёт ложное чувство контроля.

При этом автоматика уже есть: Pass E выносит вердикт, ADR-014 публикует `accept`
с порогами, спорное помечается бейджем, сообщество может блокировать. Не хватало
**измерения, насколько автоматика права**, и способа менять пороги без риска.

## 1. Решение

**Публикуем всё, кроме явного брака.** Человек — не гейт, а аудитор и разборщик
эскалаций. Политика решает не «пропустить/не пропустить», а **каким статусом доверия
опубликовать**.

| Исход | Публикация | Бейдж | Кто разбирает |
|---|---|---|---|
| `auto_accept` | да | нет | только выборка аудита |
| `badge` | да | да | сообщество |
| `quarantine` | да | да | аудит усиленный (новый домен) |
| `queue` | да | да | приоритет аудита |
| `auto_reject` | нет | — | никто |

Инвариант: `publish = outcome !== "auto_reject"`, `badge = publish && outcome !== "auto_accept"`.

## 2. Правила (порядок важен)

| # | Условие | Исход | Код причины |
|---|---|---|---|
| 1 | источник `blocked` / `duplicate` | auto_reject | `source_blocked` |
| 2 | вердикт LLM `reject` | auto_reject | `verdict_reject` |
| 3 | жёсткий флаг (`off_topic`, `wrong_language`, `duplicate`, `invalid_response`) | auto_reject | `flag_*` |
| 4 | релевантность ниже порога отказа | auto_reject | `low_relevance` |
| 5 | домен с историей блокировок | auto_reject | `domain_blocked` |
| 6 | первый материал компетенции | queue | `first_material_for_competency` |
| 7 | новый домен | quarantine | `new_domain` |
| 8 | платный доступ | badge | `paid_access` |
| 9 | мягкий флаг (`marketing`, `paywall`, `no_practice`, `outdated`, …) | badge | `flag_*` |
| 10 | конфликт с принятым материалом | badge | `conflict_with_accepted` |
| 11 | устаревание / лимит формата | badge | `stale_source` / `format_limit` |
| 12 | вердикт `accept` + уверенность и релевантность выше порогов + известный домен | **auto_accept** | `two_independent_signals` |

`auto_accept` требует **двух независимых сигналов**: LLM-вердикт и структурный контекст
(домен из реестра, база компетенции, открытый доступ). Одного сигнала недостаточно.

## 3. Сигналы и их источники

| Сигнал | Откуда |
|---|---|
| `verdict`, `confidence`, `usefulness` | Pass E (LLM-методолог) |
| `relevance` | `usefulness` из Pass E |
| `flags` | Pass E |
| `domain`, `provider`, `kind`, `language` | журнал расширения |
| `access` | каталог (журнал не содержит) |
| `domainHistory` | реестр источников (active → известен, blocked → блокирует) + принятые материалы каталога |
| `competency.hasAcceptedMaterials`, `acceptedInFormat` | каталог: материалы → компетенции через `canonicalIds` |
| `ageDays` | дата источника |

**Важная находка.** `score` из журнала расширения — это match-score со сдвинутой шкалой
(наблюдения: 0.30–0.64), а `usefulness` — оценка полезности (0.50–0.90). Если подставить
`score` в порог релевантности, политика отвергает 81% кандидатов. Поэтому `relevance`
берётся из `usefulness`, а `score` в политике не участвует.

## 4. Shadow-режим

`npm run review:shadow -- --profession it.uxui` считает политику на журнале расширения,
ничего не публикуя, и пишет отчёт в `data/reviews/shadow-<slug>-<date>.json`.

Наблюдения на `expansion-uxui-2026-11-03.json` (27 кандидатов, политика 1.0.0):

```
auto_accept  6  22%
badge        5  19%
quarantine   1   4%
queue       13  48%
auto_reject  2   7%
опубликовано 25 · скрыто 2 · с бейджем 19
```

`queue` доминирует из-за правила `first_material_for_competency`: в каталоге у этих
компетенций ещё нет принятых материалов. Это ожидаемый **холодный старт**: пока база
не накоплена, авто-приёмка ограничена по замыслу, а не по ошибке.

Сетка порогов показывает, как меняется доля `auto_accept` при разных порогах
уверенности и релевантности — пороги выбираются по данным, а не «на глаз».

## 5. Аудит вместо очереди

- Ежедневно случайная **стратифицированная выборка 3–5%** из `auto_accept`
  (по домену, провайдеру, компетенции) проверяется человеком **после публикации**.
- `auto-precision` = доля подтверждённых в выборке.
- Пороги управления: `≥ 0.97` — можно расширять автономию; `< 0.95` — ужесточить;
  `< 0.90` — вернуть страту в `queue` и разобрать.
- Новая версия политики сначала работает в shadow: сравниваем с решениями человека
  и сообщества на накопленной истории (1 385 решений по источникам уже есть).

## 6. Экономика

| Параметр | Оценка |
|---|---|
| Изменений в день (100 профессий × 3) | 300 |
| `auto_accept` (~90% в зрелом режиме) | 270 |
| `badge` / `quarantine` | ~20 |
| `queue` (приоритет аудита) | ~10 |
| Аудит-выборка 5% | ~15 |
| **Нагрузка человека** | **~25 решений/день ≈ 30 мин** |

Для сравнения: ручная приёмка всех 300 — 5–8 часов в день и падение качества внимания.

## 7. Ограничения

- `access` в журнале расширения отсутствует → правило `paid_access` пока не срабатывает;
  нужно передавать доступ из discovery.
- `conflictingAccepted` всегда `false`: конфликты материалов по компетенции ещё не считаются.
- Доменная репутация накапливается только из реестра и каталога; отдельной истории
  решений по домену пока нет — это итерация 2.

## 8. Дальше

1. Итерация 2: `ReviewDecision` в БД (сигналы + политика + исход), доменная репутация,
   карантин, аудит-выборка в админке, автодемоушен по жалобам.
2. Итерация 3: включение `auto_accept` по стратам, метрики `auto-precision`,
   автоподстройка порогов, версии политики в конфиге.

## 9. Как проверить

```bash
npm run review:shadow -- --profession it.uxui          # отчёт без публикации
npm run review:shadow -- --profession it.uxui --json   # машинный отчёт
npm run run:cli -- create --profession it.graphic      # прогон с приёмкой
npm run run:cli -- advance <runId>
```

Код: `src/methodology/v1/review/` (`policy.ts`, `signals.ts`, `shadow.ts`, `handler.ts`),
тесты: `tests/review-policy.test.ts`, `tests/review-shadow.test.ts`.
