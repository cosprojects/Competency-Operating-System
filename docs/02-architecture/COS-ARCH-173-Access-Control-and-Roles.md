# COS-ARCH-173 — Access control, роли и видимость данных

## 1. Зачем документ

Ролевая модель должна расти вместе с функциональностью. Документ фиксирует:

- какие роли есть сейчас и какие появятся;
- какие действия (capabilities) защищаются;
- кто какие данные видит;
- что делаем в MVP, а что откладываем.

Главный принцип: **не роль определяет доступ, а capability**. Роль — это именованный набор capabilities.

## 2. Ключевое разделение

Нельзя смешивать четыре разных понятия:

1. **Пользователь** — человек с аккаунтом.
2. **Платформенная роль** — глобальная роль в AXIONA (`OWNER`, `SUPPORT`).
3. **Роль в организации** — роль внутри компании/команды (`ORG_ADMIN`, `ORG_METHODOLOGIST`, `ORG_MEMBER`).
4. **Сервисный актор** — агент/автоматизация, не человек и не `UserRole`.

`ADMIN` в корпоративном контуре — это **не глобальный админ**, а `ORG_ADMIN`, ограниченный своей организацией. Иначе админ одной компании сможет видеть данные другой.

Контентный ревьюер как отдельная человеческая роль **не нужен**: контентный агент улучшается и автоматизируется. Человеческие права на контент остаются у `OWNER`; агент получает отдельный сервисный доступ и пишет в audit как `AGENT`.

## 3. Роли

### Платформенные

| Роль | Кто это | Область |
|---|---|---|
| `OWNER` | Ты, супер-админ | Вся платформа |
| `SUPPORT` | Поддержка; читает почти всё, может вести отзывы, но не меняет роли/контент | Вся платформа |
| `USER` | Обычный зарегистрированный пользователь | Свои данные |

### Сервисный актор

| Актор | Кто это | Область |
|---|---|---|
| `AGENT` | Контентный/методологический агент, автоматизация | Контент, источники, подготовка релиза; без PII |

`AGENT` не является пользователем и не входит в `UserRole`. У него отдельный токен/доступ, ограниченный capability и аудитом.

### Организационные (позже)

| Роль | Кто это | Область |
|---|---|---|
| `ORG_ADMIN` | Администратор компании/команды | Только своя организация |
| `ORG_METHODOLOGIST` | Методолог компании: маршруты развития | Только своя организация |
| `ORG_MEMBER` | Сотрудник | Свои данные в организации |

`ADMIN` как глобальную роль не вводим. В интерфейсе можно писать «Администратор команды», в коде — `ORG_ADMIN`.

## 4. Capabilities

Capabilities — атомарные проверки. Роли собираются из них.

| Capability | Что разрешает |
|---|---|
| `account:self` | Свой профиль, сохранения, статусы, удаление |
| `feedback:create` | Отправить отзыв |
| `feedback:read` | Читать очередь отзывов |
| `feedback:write` | Менять статус отзыва, отвечать |
| `metrics:read` | Читать агрегированные метрики |
| `users:read` | Читать список пользователей (без лишнего PII) |
| `users:manage` | Менять роли/статусы пользователей |
| `source-review:moderate` | Подтверждать/блокировать материалы вручную |
| `content:assemble` | Собирать/обновлять контент и источники |
| `content:publish` | Публиковать контент/релиз |
| `roles:manage` | Выдавать платформенные роли |
| `org:manage` | Управлять своей организацией/командой |
| `org:view` | Видеть прогресс своей команды |
| `audit:read` | Читать журнал админ-действий |

## 5. Матрица доступа

| Capability | GUEST | USER | SUPPORT | ORG_ADMIN | OWNER |
|---|---|---|---|---|---|
| `account:self` | — | ✓ | ✓ | ✓ | ✓ |
| `feedback:create` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `feedback:read` | — | — | ✓ | — | ✓ |
| `feedback:write` | — | — | ✓ | — | ✓ |
| `metrics:read` | — | — | ✓ aggregate | ✓ own org | ✓ |
| `users:read` | — | — | ✓ limited | ✓ own org | ✓ |
| `users:manage` | — | — | — | — | ✓ |
| `source-review:moderate` | — | — | — | — | ✓ |
| `content:assemble` | — | — | — | — | ✓ |
| `content:publish` | — | — | — | — | ✓ |
| `roles:manage` | — | — | — | — | ✓ |
| `org:manage` | — | — | — | ✓ own org | ✓ |
| `org:view` | — | — | — | ✓ own org | ✓ |
| `audit:read` | — | — | — | — | ✓ |

### Автоматизация

| Capability | AGENT | OWNER |
|---|---|---|
| `content:assemble` | ✓ | ✓ |
| `source-review:automate` | ✓ | — |
| `release:prepare` | ✓ | ✓ |
| `content:publish` | — | ✓ |

Агент готовит контент и релиз, но публикацию подтверждает `OWNER`. Это сохраняет контроль качества и не превращает автоматизацию в бесконтрольную запись.

Уточнения:

- `SUPPORT` читает почти всё, может менять статус отзыва — это часть поддержки. Не меняет роли, контент и публикацию.
- `CONTENT_REVIEWER` как роль отсутствует; контентный агент работает как `AGENT` и не видит PII.
- `ORG_ADMIN` не видит другие организации, глобальный контент и платформенные роли.
- `OWNER` — единственный, кто управляет ролями, публикацией и видит полный audit.

## 6. Видимость данных

| Данные | Кто видит |
|---|---|
| Публичные профессии/компетенции | все |
| Свои сохранения/статусы/согласия | сам пользователь |
| Email пользователя | `OWNER`; `SUPPORT` — только если нужен ответ; `ORG_ADMIN` — участники своей команды |
| Текст отзыва и контакт | `OWNER`, `SUPPORT` |
| Аналитика | `OWNER`, `SUPPORT` — агрегаты; `ORG_ADMIN` — агрегаты своей команды |
| Спорные материалы и источники | `OWNER`; `AGENT` — только контентные данные и сигналы |
| Роли и audit | `OWNER` |

Правило: если для задачи не нужен email или текст отзыва — не показываем. Агент не получает PII и не пишет в пользовательские таблицы напрямую.

## 7. Реализация по фазам

### Фаза 0 — сейчас (Beta, один админ)

Не вводим `UserRole` в БД. Делаем:

1. `OWNER_EMAILS` (можно оставить `ADMIN_EMAILS` как alias) — список email супер-админа.
2. `apps/web/src/lib/access.ts`:
   - `type Capability`;
   - `can(user, capability)`;
   - `requireCapability(capability, returnTo)` для страниц;
   - `requireApiCapability(capability)` для API.
3. `AdminAudit` в Prisma:
   - `actorId`, `actorEmail`, `action`, `targetType`, `targetId`, `meta`, `createdAt`.
4. `/admin/*` и `/api/admin/*` проверяют capability, а не `isAdminEmail`.
5. Все мутации админа пишут audit.

Почему так: email-подход уже есть; мы не ломаем его, но убираем разброс проверок и получаем журнал действий.

### Фаза 1 — поддержка/второй админ

Добавляем `UserRole` только для людей (`OWNER`, `SUPPORT`):

```prisma
enum PlatformRole {
  OWNER
  SUPPORT
}

model UserRole {
  id        String       @id @default(cuid())
  userId    String
  role      PlatformRole
  grantedAt DateTime     @default(now())
  grantedBy String?
  user      User         @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, role])
}
```

`OWNER_EMAILS` остаётся bootstrap: если email в списке и роли нет — выдаём `OWNER` при первом входе. Дальше роли живут в БД. Контентный агент остаётся сервисным актором и в `UserRole` не попадает.

### Фаза 2 — корпоративный контур

```prisma
model Organization {
  id        String   @id @default(cuid())
  name      String
  createdAt DateTime @default(now())
}

enum OrgRole {
  ORG_ADMIN
  ORG_METHODOLOGIST
  ORG_MEMBER
}

model OrganizationMember {
  id             String   @id @default(cuid())
  organizationId String
  userId         String
  role           OrgRole
  createdAt      DateTime @default(now())

  @@unique([organizationId, userId])
}
```

`ORG_ADMIN` получает `org:manage`/`org:view` только для своей `organizationId`. Это ключевое отличие от глобального `ADMIN`.

## 8. Что меняется в коде

Сейчас:

```ts
if (!isAdminEmail(user.email)) redirect(...)
```

Станет:

```ts
await requireCapability("feedback:read");
```

Для API:

```ts
const actor = await requireApiCapability("feedback:write");
await audit(actor, "feedback.status.update", "Feedback", id, { status });
```

`can()` для `OWNER` возвращает `true` на все capabilities; для `USER` — только self/feedback:create; для будущих ролей — по матрице.

## 9. Что не делаем сейчас

- Не добавляем `UserRole` и организации до появления второго админа/корп-контура.
- Не делаем отдельный admin-сервер; отдельный поддомен — позже.
- Не даём `SUPPORT` менять контент, публиковать и управлять ролями.
- Не даём `ORG_ADMIN` глобальный доступ.
- Не даём `AGENT` доступ к PII и публикации без подтверждения `OWNER`.
- Не показываем PII там, где достаточно агрегата.

## 10. Профиль и аккаунт

Это два разных пользовательских экрана:

- `/profile` — **действия пользователя в системе**: сохранённые компетенции, статусы, прогресс, история работы, последние действия. Приватная страница, не публичный профиль.
- `/account` — **данные и управление доступом**: email, согласия, сессия, удаление аккаунта.

Удаление аккаунта:

- кнопка в `/account`;
- подтверждение **модалкой**, а не `window.confirm`;
- в модалке явно перечислено, что удаляется: аккаунт, сохранения, статусы, отзывы, сессии, согласия;
- после подтверждения — удаление записей и **отзыв доступа**: сессия и cookie очищаются, пользователь выходит;
- analytics-события обезличиваются (`userId = null`), как в текущей реализации.

Текущий `DeleteAccountButton` использует `window.confirm`; его нужно заменить на модалку. API `/api/account/delete` уже удаляет пользователя и очищает сессию — логику сохранить, UI доработать.

## 11. Решения

1. `SUPPORT` может менять статус отзыва — **да**.
2. `CONTENT_REVIEWER` как человеческая роль **не нужен**; контентный агент автоматизируется как `AGENT`, публикация остаётся за `OWNER`.
3. Профиль — отдельный `/profile`; аккаунт — отдельный `/account` с удалением через модалку.
4. `ORG_ADMIN` вместо глобального `ADMIN` — **да**.
5. Для Beta: `OWNER_EMAILS`/`ADMIN_EMAILS` + capability-слой + `AdminAudit`; `UserRole` не вводим, пока нет второго человека-админа/поддержки.
