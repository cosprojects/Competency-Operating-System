# Access model

Это отдельный источник ролевой модели AXIONA. Он отвечает на вопросы:

- какие роли есть сейчас, какие запланированы;
- какие capabilities существуют;
- кто какие данные видит;
- что реализовано, что только на бумаге;
- как менять модель, не ломая доступ.

## Файлы

- [`roles.json`](roles.json) — machine-readable модель: роли, capabilities, матрица, видимость, фазы.
- [`COS-ARCH-173`](../COS-ARCH-173-Access-Control-and-Roles.md) — объяснение решений и контекст.

`roles.json` — источник правды для реализации. При добавлении функции сначала появляется capability в JSON, затем проверка в коде, затем роль/выдача.

## Решения (2026-10-28)

- `OWNER` — супер-админ, определяется по email (`OWNER_EMAILS`, alias `ADMIN_EMAILS`) на этапе Beta.
- `SUPPORT` — включаем **после первой версии**, когда появятся отзывы и станет понятен объём поддержки.
- `CONTENT_REVIEWER` как человеческая роль **не нужен**. Контентный агент — сервисный актор `AGENT`; публикация остаётся за `OWNER`.
- `ORG_ADMIN` / `ORG_METHODOLOGIST` / `ORG_MEMBER` — только на бумаге до корпоративного контура.
- `UserRole` в БД сейчас **не вводим**: для Beta достаточно email-владельца.
- `AdminAudit` вводим уже сейчас: журнал админ-действий нужен до публичной Beta.
- Экспорт профиля перед удалением аккаунта **не нужен**.
- Профиль и аккаунт разделены: `/profile` — действия пользователя, `/account` — данные и удаление доступа через модалку.

## Как менять модель

1. Добавить capability в `roles.json` и матрицу.
2. Обновить `COS-ARCH-173`, если меняется правило видимости.
3. Реализовать проверку через `requireCapability` в коде.
4. Добавить audit для мутации.
5. Обновить тесты доступа.
6. Только после этого выдавать роль человеку.

Не добавляй роль без capability и не добавляй capability без проверки в коде.
