# COS-EAR-012 — Реализованные пользовательские сценарии Beta 1

## 1. Назначение и границы

Документ описывает **только то, что реализовано и работает** в приложении `apps/web` на коммите `6f5b1c6` (2026-10-28): экраны, шаги, состояния, гейты и данные. Это вход в дизайн: что уже есть, какие состояния обязаны быть нарисованы, чего в продукте нет.

Не описывает:

- **Целевой слой диагностики** `COS-EAR-009` (S0 Landing → S1 Setup → S2 Evidence → S3 Gate → S4 Result). В коде его нет; реестр `COS-REL-007` (§2) помечает `COS-EAR-009` как «Будущий этап», ADR-001 `COS-REL-008` — как следующий слой. Дизайн по `COS-EAR-009` описывал бы несуществующий продукт.
- Контентный пайплайн (`src/methodology`, `scripts/release`, `catalog/`, `model/`) — вне UI.
- Внутренние операции вне `/admin/*`.

Источник истины — код. Расхождения документов с кодом собраны в §9; они не исправлены в этом документе (только зафиксированы).

Место описанных сценариев в дорожной карте — §13.

## 5. Сквозные правила

1. **Гейт материалов.** Внешняя ссылка на материал не показывается анониму: вместо неё кнопка «Войти и открыть» с `returnTo` на текущую компетенцию (`components/SourceLink.tsx:18-33`). Весь остальной контент — определения, знания, навыки, названия и описания материалов — открыт без входа.
2. **Гейт аналитики.** События пишутся только при cookie `axiona_consent=all`; при значении `necessary` продукт работает без событий (`client-analytics.ts:5-28`, `lib/analytics.ts:13-19`, `api/events/route.ts:17-20`). Cookie живёт 180 дней, интерфейса смены решения нет.
3. **Аутентификация.** Токен 32 байта, в БД SHA-256, TTL 15 минут, одноразовый, погашается только POST; сессия 30 дней, cookie HttpOnly/Secure/SameSite=Lax (`auth.ts:5-7,137-146`). Открытый redirect запрещён — только внутренние пути, иначе `/saved` (`auth.ts:169-175`).
4. **Анти-абьюз.** Rate limit в памяти процесса: вход 5/час на email и 20/час на хэш IP, отзывы 5/час на IP, события 300/час на IP (`auth.ts:177-194`, `api/auth/request:33`, `api/feedback:13`, `api/events:23`); плюс проверка числа токенов по БД (`api/auth/request:37-40`). Лимиты сбрасываются при рестарте и не общие между инстансами.
5. **CSRF/Origin.** Все мутации проверяют Origin (`sameOrigin`, `auth.ts:203-219`).
6. **Статус контента.** Пока `beta-1.json` в `status: draft`, над каждой страницей показывается черновая плашка «Не публиковать без release:validate и status=ready» (`app/layout.tsx:32-38`). Сейчас — draft, то есть плашка видна везде.
7. **Поведение без БД.** Анонимные страницы работают без БД (сессия читается только при наличии cookie). При недоступной БД и живой сессии `Header` упадёт в `error.tsx`.

### 6.4 B1-S4 — Открытие материала и требование входа

| | |
|---|---|
| Роль | Аноним → пользователь |
| Цель | Перейти к курсу или статье |
| Шаги | Карточка материала → «Войти и открыть» (событие `source_gate_view`) → `/login?returnTo=/competencies/[id]` → email → письмо → `/auth/verify?token=…` → «Войти» → возврат на компетенцию → «Открыть материал» (внешняя вкладка, `target=_blank rel="noopener noreferrer"`) |
| Состояния | Для вошедшего гейт не показывается вовсе. Для анонима — кнопка вместо ссылки, других объяснений нет |
| Данные | `returnTo` сохраняется в `LoginToken` и переживает переход по письму (`auth.ts:49-65,77-135`) |
| События | `source_gate_view` → `signup_start` → `signup_complete` → `source_click` |
| Заметки | Это единственная причина регистрации в продукте. Стоимость: аноним не может перейти ни к одному материалу, хотя видит его описание |

### 6.5 B1-S5 — Вход по ссылке (основной поток)

| | |
|---|---|
| Роль | Аноним |
| Цель | Получить аккаунт и доступ к материалам |
| Шаги | `/login` → email + чекбокс «принимаю условия и политику, мне 18+» (обязателен, без него кнопка неактивна) → «Получить ссылку» → инлайн «Проверьте почту» → письмо (локально — в консоль, `email.ts:23-29`) → `/auth/verify?token=` → «Войти» → редирект на `returnTo` или `/saved` |
| Состояния | `idle` → `sending` («Отправляем…») → `sent` (форма заменена подтверждением + «запросите новое») → `error` (текст из API). Пустой/некорректный email — ошибка «Проверьте email» |
| Приватность | Ответ на запрос всегда одинаковый, наличие аккаунта не раскрывается (`api/auth/request:56-57`); consents TERMS/PRIVACY пишутся в БД (`auth.ts:107-118`) |
| События | `signup_start`, `signup_complete` |
| Заметки | Локально письма нет — путь проходится только через консоль сервера. В production без `EMAIL_API_URL` отправка падает 503 (`email.ts:24-26`) |

### 6.6 B1-S6 — Ошибки входа и восстановление

| Ситуация | Фактическое поведение |
|---|---|
| Токен истёк / уже использован / неверный | POST `/api/auth/verify` → 303 на `/login?error=link`. **Страница входа этот параметр не читает** (`app/login/page.tsx` передаёт в форму только `returnTo`) → человек видит чистую форму без объяснения |
| Токен отсутствует в ссылке | «Ссылка неполная» + кнопка «Запросить ссылку» (`auth/verify/page.tsx:16-26`) |
| Сканер почты открыл ссылку | GET только показывает страницу, токен не гасится (`api/auth/verify` — только POST) |
| Чужой Origin | 303 на `/login?error=origin`; параметр также не отображается |
| Превышен лимит запросов | API молча отвечает `{ok:true}` (`api/auth/request:33-35`), интерфейс показывает «проверьте почту» — человек ждёт письмо, которого не будет |
| Email-провайдер недоступен | 503 «Не удалось отправить письмо. Попробуйте позже.» |
| Ссылка открыта в другом браузере | Работает: сессия создаётся после POST в том браузере, где нажали |

### 6.7 B1-S7 — Сохранение в избранное

| | |
|---|---|
| Роль | Пользователь |
| Цель | Вернуться к компетенции или материалу |
| Шаги | На `/competencies/[id]` — «☆ Сохранить» (сохраняется компетенция). Материал: кнопка `SaveButton` с `targetType="SOURCE"` есть только на `/saved`, в карточке материала (`SourceList` не содержит кнопки сохранения) |
| Состояния | `saved` → «★ В сохранённом», повторное нажатие удаляет; ошибка — «Не удалось сохранить. Попробуйте ещё раз.», состояние откатывается; `disabled` пока идёт запрос |

### 6.8 B1-S8 — Статус изучения

| | |
|---|---|
| Роль | Пользователь |
| Цель | Отметить личный прогресс |
| Шаги | На `/competencies/[id]` — один из трёх сегментов: «Не изучено», «Изучаю», «Изучено» |

### 6.9 B1-S9 — Сохранённое

| | |

| Роль | Пользователь |
| Цель | Вернуться к сохранённому |

## 10. Пробелы и риски

**Функциональные разрывы (влияют на дизайн):**

1. **Нельзя сохранить материал с карточки материала.** `SaveButton` с `targetType="SOURCE"` есть только в `/saved`; на странице компетенции кнопка сохраняет компетенцию (`components/SourceList.tsx`, `app/competencies/[id]/page.tsx:79-84`). Сценарий «сохранить полезный курс» из основного пути недостижим.
2. **Тихая потеря ошибок входа.** `?error=link|origin` не отображается; при 429 человек видит «проверьте почту» и ждёт письмо.
3. **Контекст профессии теряется у общих компетенций.** 34 из 54 компетенций входят в несколько профессий; хлебные крошки и `profession_id` в событии берутся из первого вхождения (`content.ts:32-38`, `app/competencies/[id]/page.tsx:16-18,52-60`). Пришёл из Product — в крошках может быть UX/UI.
4. **Prerequisites сырыми id** — дефект интерфейса: на экране видно `ux-user-research` вместо названия; попадёт на макеты, если не исправить до дизайна.
5. **Дубль `study_status_change`** искажает метрику использования.
6. **`/login/check-email` как мёртвый маршрут** — лишний экран в IA, если попадёт в навигацию.
7. **Мобильная навигация:** на ≤640px нет пунктов «Сохранённое» и «Обратная связь»; попасть в `/saved` можно только через редирект после входа.
8. **Нет поиска и фильтрации** ни в одном списке; 34 компетенции одной профессии прокручиваются одним полотном.
9. **Нет визуального признака активного раздела** в шапке; хлебные крошки есть на `/professions/[slug]`, `/competencies/[id]`, `/feedback`, `/canvas/[slug]`, но отсутствуют на `/professions`, `/canvas`, `/saved`, `/account`.
10. **Смешение двух карт:** `/professions/[slug]` (Beta-контент, 34/30/28/18) и `/canvas/[slug]` (генерируемые схемы, другой набор и число узлов). Для пользователя это два разных представления одной профессии без объяснения связи.

**Риски:**

- Черновая плашка «Не публиковать» видна на всех страницах, пока контент в `status: draft` — любой дизайн-макет должен либо её учитывать, либо фиксировать, что она снимается релизом.
- Rate limit в памяти: на нескольких инстансах лимит становится «N на инстанс»; поведение под нагрузкой не проверено.
- `Header` ходит в БД при наличии cookie сессии: при недоступной БД залогиненный пользователь увидит `error.tsx`, аноним — нормальную страницу.
- 8 research-схем публичны и не проходят content gate: противоречие с позиционированием «в Beta только проверенное».

## 11. Открытые вопросы

1. **Гейт материалов.** Остаётся ли требование входа для открытия внешних ссылок в Beta? От этого зависят CTA, объяснение ценности регистрации и вся воронка `source_gate_view → signup_complete`.
2. **Роль `/saved`.** Это «Мой»-хаб или технический список? Нужно ли редактирование статусов, прогресс по профессии, сортировка — или только два списка, как сейчас?
3. **Поиск и фильтры.** Входят ли поиск/фильтр по tier и разделу в Beta, или списки остаются полотном до post-Beta? Это меняет IA профессии и мобильную навигацию.
4. **Схемы в публичном продукте.** Оставляем ли 8 research-схем открытыми и как объясняем связь «схема ↔ карта профессии»?
5. **Момент дизайна.** Проектируем ли интерфейс под `status: draft` (с плашкой) или сразу под публичный `status: ready`?

## 12. Рекомендации

Порядок — от дешёвого и блокирующего к продуктовым решениям.

1. **До дизайна починить 4 видимых дефекта:** текст prerequisites (название вместо id), отображение `?error=link|origin` на `/login`, кнопка сохранения материала на карточке материала, убрать/переиспользовать `/login/check-email`.
2. **Свести отзыв к одному паттерну:** одна форма, контекст передаётся, входы — из карточки компетенции, материала и футера.
3. **Синхронизировать документы** по §9: `COS-REL-003:66` (схемы), `COS-REL-004` (события `profession_view`, `return_visit`, дубль `study_status_change`), добавить `COS-EAR-012` в реестр `COS-REL-007` и отметить в `COS-EAR-009`, что это target, а не текущий flow.
4. **Определить дизайн-скоуп по ответам §11** — иначе макеты покроют либо несуществующий слой диагностики, либо недоделанные места.
5. **Перед макетами зафиксировать инвентарь состояний** из §7: генерация макетов без пустых/ошибочных состояний повторит текущую проблему «состояния есть в коде, но не нарисованы».
