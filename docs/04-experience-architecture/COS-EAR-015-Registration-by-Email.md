# COS-EAR-015 — Регистрация по email

## 1. Назначение и границы

Спека описывает публичную self-serve регистрацию по email: экраны, тексты, состояния, данные и критерии приёмки. Механизм — magic link без паролей (`COS-REL-008`, ADR-005 и ADR-022). В интерфейсе не используем слово «регистрация» как название шага: человек создаёт аккаунт по ссылке из письма (`COS-SCN-005` §5.3).

Не описывает: пароли, OTP, OAuth, восстановление пароля, редактирование профиля, маркетинговые рассылки, платный слой.

## 2. JTBD

**Основная работа.** Когда я нашёл полезный материал или хочу вернуться к компетенциям, мне нужно личное место, где всё сохраняется, — без пароля и анкеты.

**Дополнительные работы.**

- Понять, зачем оставлять email и что я получу.
- Вернуться к сохранённому с другого устройства.
- Не заполнять пароль и не бояться его забыть.

**Чего человек не хочет.** Анкеты до пользы, пароля, «подтвердите почту, чтобы посмотреть», непонятных писем без объяснения.

## 3. Сценарии

| Сценарий | Вход | Выход |
|---|---|---|
| Новый аккаунт | `/register?returnTo=…` | Письмо → `/auth/verify` → аккаунт, welcome-письмо, `/saved?welcome=1` или `returnTo` |
| Возврат | `/login?returnTo=…` | Письмо → `/auth/verify` → вход, согласие фиксируется по факту подтверждения |
| Инвайт владельца | Письмо-приглашение | `/auth/verify` → аккаунт; согласие фиксируется тем же подтверждением |
| Материал за гейтом | Кнопка «Войти и открыть» на компетенции | `/register?returnTo=/professions/<slug>?competency=<id>` |

## 4. Экраны и тексты

### 4.1. `/register`

- Заголовок: «Создай аккаунт в AXIONA».
- Пояснение: «Сохраняй компетенции и материалы, возвращайся к ним с любого устройства и собирай личный профиль. Без пароля: вход по ссылке из письма.»
- Поле Email, кнопка «Создать аккаунт».
- Пассивная строка под полем, как в макете (`Figma UfuaPpLJA31DeBSObX5xNJ`, узел `250-37419`): «Нажимая «Создать аккаунт», ты принимаешь Условия использования и Политику конфиденциальности». Чекбокса нет.
- Ссылка «Уже есть аккаунт? Войти».

### 4.2. `/login`

- Заголовок: «Войди в AXIONA».
- Та же пассивная строка: «Нажимая «Войти», ты принимаешь Условия использования и Политику конфиденциальности».
- Кнопка «Получить ссылку для входа», ссылка «Нет аккаунта? Создать аккаунт». В макете кнопка и фраза согласия расходятся (фраза про «Войти») — временно повторяем макет, правка на следующей ревизии дизайна.

### 4.3. Состояние «письмо отправлено»

«Проверь почту». Текст: «Если адрес … может получать письма, мы отправили ссылку. Она действует 15 минут и работает один раз.» Подсказка про «Спам» и кнопка «Запроси новое».

### 4.4. `/auth/verify`

- Заголовок «Подтверди вход», пояснение «Нажми кнопку, чтобы войти в AXIONA. Ссылка одноразовая и действует 15 минут.», кнопка «Войти».
- Чекбокса согласия на этой странице нет: согласие оформлено пассивной строкой на форме входа/регистрации (как в макете) и фиксируется записями `ConsentRecord` в момент погашения ссылки.
- Повторное открытие страницы не гасит токен — погашение только по кнопке (защита от почтовых сканеров).

### 4.5. После создания аккаунта

- `/saved?welcome=1` с блоком «Аккаунт создан. Здесь появятся сохранённые профессии и компетенции»; параметр убирается из адреса без перезагрузки.
- Welcome-письмо: что уже доступно и куда идти; отправка best-effort и не ломает вход.

## 5. Состояния и ошибки

| Ситуация | Поведение |
|---|---|
| Некорректный email | Ошибка «Проверь email», письмо не уходит |
| Ссылка истекла / использована / битая | `/auth/link-invalid`: «Ссылка больше не действует» + «Запросить ссылку» |
| Токен отсутствует в ссылке | «Ссылка неполная» + «Запросить ссылку» |
| Превышен лимит запросов | Одинаковый ответ «проверь почту»; интерфейс не раскрывает лимит |
| Провайдер email недоступен | 503 «Не удалось отправить письмо. Попробуй позже.» |
| Honeypot заполнен | Тихо `ok` без письма |
| `AUTH_REGISTRATION_DISABLED=1` | Новые адреса письма не получают; существующие входят; инвайты работают |
| Нет БД (demo) | POST подтверждения ведёт на `/auth/link-invalid`; регистрация не открывается |
| `returnTo` внешний | Подменяется на `/saved` |

## 6. Критерии приёмки

1. Given новый посетитель на `/register`, When вводит корректный email, Then письмо уходит, ответ одинаковый и не раскрывает существование аккаунта.
2. Given новый email, When открывает ссылку, Then видит подтверждение без чекбокса и с кнопкой «Войти»; GET по ссылке токен не гасит.
3. Given подтверждает, Then создаётся `User`, пишутся `ConsentRecord` TERMS/PRIVACY за `LEGAL_VERSION`, ставится сессия, отправляется welcome-письмо, редирект `/saved?welcome=1` (или `returnTo`), при согласии на аналитику — `signup_complete`.
4. Given существующий пользователь, When открывает новую ссылку, Then входит в один клик; welcome и `signup_complete` не срабатывают, согласия за актуальную версию не дублируются.
5. Given админский инвайт, When приглашённый подтверждает ссылку, Then аккаунт и согласия создаются тем же путём.
6. Given использованная ссылка, Then `/auth/link-invalid`; GET по ссылке токен не гасит.
7. Given honeypot заполнен, Then письмо не отправляется, ответ `ok`.
8. Given `AUTH_REGISTRATION_DISABLED=1`, Then новые адреса письма не получают, существующие получают, инвайты работают.
9. Given `/saved?welcome=1`, Then приветствие видно один раз.
10. Unit-тесты покрывают `safeReturnTo`, лимиты, origin, honeypot и политики регистрации.

## 7. Данные

- `LoginToken`: email, `tokenHash` (SHA-256), TTL 15 минут, `purpose` (`login`/`invite`), `returnTo`, `consentVersion`, `usedAt`.
- `Session`: `tokenHash`, TTL 30 дней; cookie `__Host-axiona_session` в production.
- `ConsentRecord`: TERMS/PRIVACY, версия `LEGAL_VERSION`, уникальность `[userId, kind, version]`.
- `User`: создаётся при первом подтверждении; `createdAt` — дата регистрации для админки.
- Схема Prisma не меняется: новые таблицы не нужны.

## 8. Аналитика

- `signup_start` — осознанное начало регистрации с `/register` (не каждый вход).
- `signup_complete` — только первое создание аккаунта; пишется при согласии на аналитику.
- Число регистраций в админке — по `User.createdAt`, без зависимости от согласия.

## 9. Вне рамок и открытые вопросы

- Пароли, OTP, OAuth, восстановление пароля.
- Капча и внешние анти-абьюз-сервисы (ADR-004 запрещает внешние runtime-сервисы); сейчас honeypot + лимиты.
- Общий стор лимитов для нескольких инстансов.
- Локализация писем и интерфейса.
- Публичное открытие регистрации — ops-gate ADR-004 (хостинг, legal, T-007).
- Пассивное согласие (без чекбокса) выбрано по макету; для выпуска в СНГ — юридическая проверка на требование явного согласия, при необходимости чекбокс возвращается (ADR-022).
