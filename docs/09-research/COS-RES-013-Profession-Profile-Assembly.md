# COS-RES-013 — Сборка профиля профессии из свидетельств ESCO

## 1. Назначение

Документ описывает сборку профиля профессии: целевое дерево компетенций, заполненное свидетельствами открытого источника. Дерево нужно, чтобы видеть, какие листья подтверждены, какие остались пробелом и какие навыки источника в дерево не входят.

Это не новый способ доказать компетенцию. Доказательством остаётся запись источника с описанием. Сборка организует выдачу для человека и не пишет граф.

## 2. Границы

- Профиль не меняет `src/methodology/v1/design-competency-graph.json` и не поднимает `methodologyVersion`.
- Уровни `L0–L3`, `targetLevel`, самооценка и оценка человека в профиль не входят.
- Сборка не утверждает полноту профессии. Лист без свидетельства — пробел, а не отсутствие компетенции.
- Инструмент не является компетенцией. Инструменты попадают в ветку `Design Tools` с видом `tool` и исключаются из диагностики графа.
- Универсальная база — листья со `scope: universal` (типографика, теория цвета, композиция). Они относятся ко всем дизайнерам, поэтому подтверждаются доменными занятиями (`art director`, `desktop publisher`) и отдельными записями ESCO, а не требованиями одной профессии. Привязка к конкретной профессии для них не требуется, но запись и её описание обязательны.
- Маппинг — организация выдачи, а не соответствие узлу графа. Сходство названий доказательством не считается.
- В профиль не попадают названия, придуманные моделью. Все названия — записи ESCO. LLM в этой версии не используется.

## 3. Входы

| Вход | Файл / адрес | Что задаёт |
|---|---|---|
| Целевая таксономия | `src/methodology/v1/profile/taxonomy/<profession>.json` | ветки, группы, листья, вид и область (`scope`) каждой цели |
| Маппинг ESCO | `src/methodology/v1/profile/mapping/<profession>.json` | занятия-источники, правила `название ESCO → цель`, причины отброса |
| Универсальная база | там же: `universalOccupations`, `universalSkills` | доменные занятия и записи ESCO для листьев `scope: universal` |
| O\*NET | там же: `onet`; [Software Skills 31.0](https://www.onetcenter.org/dl_files/database/db_31_0_csv/software_skills.csv) | инструменты и их статус (Hot Technology, In Demand) для `15-1255.00`; лицензия CC BY 4.0 |
| Guidance | там же: `guidanceSources`, `guidanceSkills` | публичные руководства с открытой лицензией; цитата обязана найтись на странице |
| Модель COS | там же: `modelSkills`; [design-competency-graph.json](src/methodology/v1/design-competency-graph.json) | узел графа и дословная цитата якоря. Внутренний слой, не внешний источник |
| Watchlist | там же: `watchlist` | листья без официальной записи; в требования не засчитываются |
| Источник ESCO | ESCO API (`resource/occupation`, `resource/skill`), `v1.2.0` | записи навыков, описания, связи с занятиями |
| Кеш | `data/profile/source-cache/` | повторный прогон без сети; сбрасывается флагом `--refresh` |
| Диагностика | `design-competency-graph.json`, `profession-catalog.json` | текущий граф и открытые профессии |

Для UX/UI выбрано пять занятий ESCO: `user interface designer` и `user experience analyst` — ядро, `ICT usability tester`, `ICT accessibility tester`, `graphic designer` — поддержка. Для универсальной базы добавлены `art director` (design principles) и `desktop publisher` (typography). O\*NET даёт инструменты, GOV.UK Service Manual — guidance по персонам. Одно занятие не покрывает и UI, и UX, а его optional-навыки содержат десятки языков программирования, поэтому источник задаётся набором, а не одной ссылкой.

## 4. Порядок сборки

1. Читаются занятия ESCO из маппинга, ссылки на навыки складываются в один список.
2. Навык дедуплицируется по записи ESCO: одна запись — одна строка, сколько бы занятий её ни назвали. Свидетельства занятий сохраняются.
3. Каждый навык проверяется по маппингу. Правило нашлось — навык идёт в дерево. Не нашлось — проверяются правила отброса с причиной. Не нашлось ни того, ни другого — навык пишется в «не сопоставлено».
4. Добавляются записи универсальной базы: правило `universalSkills` берёт запись из доменного занятия по названию или напрямую по `escoUri`; цель обязана быть универсальным листом.
5. Читается O\*NET Software Skills (CSV официальной базы, кешируется): строка инструмента ищется по SOC-коду и `Workplace Example`. Найденная запись сохраняет факты строки: Hot Technology и In Demand.
6. Читаются guidance-страницы. Цитата нормализуется и ищется в тексте страницы; если её нет — правило не подтверждает лист и попадает в `guidanceMissing`.
7. Читаются правила модели COS: цитата обязана найтись в полях узла графа (название, описание, якоря). Иначе — `modelMissing`.
8. Для записей ESCO читается описание навыка. Цитата сохраняется как есть.
9. Строится дерево. Статус листа: `supported` — есть внешнее свидетельство с описанием (ESCO, универсальная база, O\*NET, guidance); `model_only` — только якорь графа; `watchlist` — официальной записи нет; `no_evidence` — пробел. Записи уровня группы и ветки показываются отдельно.
10. Выполняется диагностика сопоставления с текущим графом методологом (`methodologist/decide.ts`). Это не запись требований.
11. Пишутся журнал профиля, человекочитаемое дерево и очередь на проверку.

## 5. Правила

- Правило маппинга обязано иметь `basis` — почему источник поддерживает именно эту цель.
- Правила без источника не прячутся: `mappingMissing` (ESCO), `universalMissing`, `onetMissing`, `guidanceMissing`, `modelMissing`.
- Причины отброса перечисляются по группам (`programming_language`, `software_engineering`, `project_management`, `other_domain_motion_3d`, `media_production`, `business_admin`, `legal_policy`, `data_ai_infra`, `transversal`). Молча ничего не отбрасывается.
- Одна запись ESCO может подтверждать несколько листьев только тогда, когда её описание прямо называет оба предмета. Для этого у правила есть `additionalTargetIds`. Области целей обязаны совпадать.
- Доказательство зависит от слоя: ESCO — дословное описание записи; O\*NET — строка Software Skills (Workplace Example, Hot Technology, In Demand); guidance — дословная цитата со страницы; модель COS — дословная цитата поля узла. Выдуманные цитаты и названия не принимаются.
- Инструмент не является компетенцией. O\*NET и ESCO дают инструменты в ветку `Design Tools` с видом `tool`; из диагностики графа они исключаются.
- Watchlist — не подтверждение. Лист watchlist не считается требованием и ждёт рыночного или отраслевого источника. Внешний вид отчёта это подписывает.
- Универсальная запись без описания источником не считается.
- Повторный прогон идемпотентен: ключ записи — профессия + запись источника + название, дубликатов не появляется.
- Стоимость прогона — запросы к открытым API и CSV; платные ключи не нужны. LLM в этой версии не используется.

## 6. Что пишет код

```bash
npm run profile:build -- --profession uxui
npm run profile:build -- --profession uxui --refresh   # перечитать источники
npm run profile:build -- --profession uxui --no-cache  # без кеша
```

| Файл | Содержимое |
|---|---|
| `data/profile/<profession>.json` | полный журнал: источники, дерево, записи, отбросы, пробелы, пропуски источников, диагностика |
| `data/profile/<profession>.md` | дерево для чтения человеком |
| `data/profile/<profession>-review.json` | записи, которым нужен человек: нет описания, неоднозначное соответствие, новый узел, пробелы, watchlist |

Во всех файлах `writesToGraph: false`. Шаг встроен в `src/methodology/v1/pipeline.json` под id `profile-build`.

## 8. Что не входит и что дальше

- **Рыночный контур.** hh.ru API вернул `403 forbidden` (DDoS-Guard). Обход защиты не делаем: это нарушает правила и позиционирование продукта. Нужен официальный доступ, партнёрская выгрузка или другой открытый API.
- **Профстандарты и ФГОС** — следующий внешний источник для `Grids`, `Information Architecture`, `Personas`, `High-Fidelity`, чтобы снять статус `model_only` и «нужна проверка».
- **O\*NET API** не обязателен: база Software Skills используется файлом. `ONET_API_KEY` нужен только для детальных задач и work activities.
- Уровни, кейсы и персональная оценка — после устойчивости модели.
- Приёмка метода на независимой размеченной выборке — по `COS-ARCH-002`; текущий прогон её не заменяет.

## 9. Проверка

`tests/profile.test.ts` (69 тестов всего по проекту) проверяет: корректность таксономии и маппинга; дедупликацию одной записи из двух занятий; сохранение цитаты; различение `supported`, `model_only`, `watchlist` и `no_evidence`; правило без источника; мульти-цель одной записи; O\*NET CSV и Hot Technology; guidance-цитату и её отсутствие; цитату якоря графа; маркировку инструмента; отсутствие записи в граф и отрисовку дерева.
